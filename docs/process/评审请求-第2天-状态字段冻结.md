# 第 2 天 · 状态字段冻结评审请求（发给 A 和 C）

## 用法

1. 先跑完提示词里的 **T1**，拿到 `docs/state-contract.md`，连同本文件一起发出去。
2. **第 1 段「群内开场」**发到四人群里；然后把 A 段单独发给 A、C 段单独发给 C。
3. 每条目都写了「我的默认」和「请你回」，对方只需要回 `确认`／`改成 X`／`待定+日期`，不用长篇讨论。
4. 手册 M1 要求当晚完成跨模块评审。请在开场里填一个明确的截止时刻（建议：当天 22:00 前）。
5. 谁没回也不要干等——按「兜底」栏继续做 T2，但要把该条记进第 3 天的阻塞清单。

> 下面三段用 ```` 代码块包起来，整段复制即可，不会丢掉格式。

## 第 1 段 · 群内开场

```text
【第 2 天 · 接口冻结评审】请 A、C 在今晚 22:00 前回复

我把第一天原型（index.html）里所有前端状态字段抽成了一份契约：
docs/state-contract.md

现在这些字段是我一个人定的，第 5 天要接真实接口、第 6 天全员联调。
手册 M1 里程碑写的是「不能带着含糊字段进入开发」，所以需要你俩确认
自己负责的那部分口径。

A：第 2 节，10 条
C：第 3 节，11 条
B：不用评审，第 4 节是知会，扫一眼就行

每条我都给了默认取值，回「确认」或「改成 X」即可。
有一条我答不了但必须定的，麻烦直接说，我们当晚定掉，不要留到第 3 天。

截止没回的，我按默认值开工，之后要改会算进第 6 天联调成本。
```

## 第 2 节 · 发给 A（会话状态与错误码后端）

```text
@A 状态字段冻结 · 需要你确认 10 条

依据：docs/state-contract.md（第 2 天 T1 产出）
背景：手册 9.2 跨模块改动由你复核，M1 今晚要冻结。
回复格式：每条回「确认」或「改成 X」。

────────────────────────────────
1. 幂等键怎么承载
   我的默认：放在请求体字段 action_id，服务端保留 10 分钟去重
   请你回：请求体 or 请求头？字段名？保留时长？
   （ia-design 第 9 节我自己写了"不擅自规定字段"，所以这条必须你定）
   不定的后果：第 5 天接真接口当天要改传输方式，提交层重写

2. version 谁递增
   我的默认：服务端是唯一真值，响应里返回新 version，前端不再自增
   现状：mock 里是前端 S.version++，第 5 天要删掉
   请你回：新 version 是随提交响应返回，还是要前端再 GET 一次？
   不定的后果：报价板 V4、协议抽屉 V3，验收第 8 条直接挂

3. VERSION_CONFLICT 时给不给条款级 diff
   我的默认：响应里带服务端当前 5 条条款快照，前端做可视差异 + 手动合并
   请你回：只返回错误码，还是给条款数据？字段名？
   不定的后果：冲突条只能退化成"拉最新覆盖草稿"，违反失败保留草稿

4. 6 个错误码是不是全集
   我的默认：只有 INVALID_ACTION / SESSION_BUSY / MODEL_UNAVAILABLE /
             ROUND_LOCKED / VERSION_CONFLICT / TIMEOUT；detail 是人类可读中文
   请你回：是否还有鉴权失败、限流、Schema 校验失败等？
   不定的后果：未预期的码会走 else 分支静默，手册明令禁止静默失败

5. 超时阈值与自动重试
   我的默认：前端等 8 秒判 TIMEOUT；SESSION_BUSY 自动重试 1 次、间隔 500ms，
             之后转手动，两次都复用同一 action_id
   请你回：后端自身超时是多少毫秒？重试会不会在后端重复执行？
   不定的后果：前端 3 秒判超时、后端 10 秒才返回，同键重提可能产生真实两笔行动

6. 模型挂了报价接口是否照常可用
   我的默认：可用。MODEL_UNAVAILABLE 只让战情解说和情报视图降级为空态，
             报价板和行动预演不依赖模型，继续工作
   请你回：是否同意这个架构前提？
   不定的后果：模型一挂整页不可操作，M2 固定场景闭环跑不完

7. 一轮提交的请求体形状
   我的默认：{ action_id, version, round, terms:[{id,value,status}], card_id|null }
             terms 传全量 5 条（不做增量 diff），无卡时 card_id 为 null
   请你回：全量 or 增量？卡牌字段叫什么？还需要别的吗？
   不定的后果：第 6 天联调我只能改前端去凑你的接口

8. 对方响应怎么回来 ← 这条最影响工作量
   我的默认：提交响应里同步返回对方反报价与发言
   备选：轮询 / SSE / WebSocket
   请你回：哪种？如果异步，消息形状和字段名是什么？
   不定的后果：你以为我改几个调用点，实际我要引入整套订阅和状态机，
               第 5～6 天不够用，会直接吃掉联调窗口

9. 轮次推进与终局由谁判定
   我的默认：服务端判定并返回新 round 与 ended 标志，前端 endRound 不再自增
   请你回：同意？终局触发条件（第 6 轮结束 / 接受协议）由后端还是前端把关？
   不定的后果：前端进 R4、后端还在 R3

10. 连接态 connecting/live/busy/locked 由谁给
    我的默认：前端自己根据请求在途与否推断，不做真信号
    请你回：后端有没有会话级状态可返回？没有的话我就继续本地推断（会在
            第 9 天冻结前标注为已知边界）
    不定的后果：顶栏灯和手牌禁用只能靠猜，演示时可能出现"看着能用其实被锁"

────────────────────────────────
如果某条你现在定不了，请回「待定 + 最晚哪天能定」，不要空着不回。
```

## 第 3 节 · 发给 C（规则、审计与复盘数据）

```text
@C 状态字段冻结 · 需要你确认 11 条

依据：docs/state-contract.md
回复格式：每条回「确认」或「改成 X」。

【教练评分 speaker_score】

1. 返回时机
   我的默认：终局时一次性返回
   请你回：只在终局，还是每轮都返回阶段性分？
   不定的后果：复盘页面做错的时机，第 8 天返工

2. 首轮 null 由谁判定
   我的默认：改成由你返回 null，前端不再用 round===1 自己判
   现状：第一天原型是前端兜底判的
   请你回：能否保证第 1 轮 speaker_score 返回 null？
   不定的后果：前端兜底会掩盖后端"该返 null 却没返"的 bug

3. 给四维原始分，还是已加权总分
   我的默认：你给四维原始分 + 已加权的 total（取整），前端不重算
   请你回：加权在哪边做？取整口径（四舍五入 or 向下）？
   不定的后果：前后端各算一次，出现两套分数，评审当场被抓

4. S/A/B/C/D 区间边界
   我的默认：90-100→S，70-89→A，50-69→B，30-49→C，0-29→D
   请你回：89.5 归哪档？0-100 之外会不会出现？
   不定的后果：评委问"为什么 89 分是 A"我答不上来

5. feedback 字段
   我的默认：你返回 20-40 字一句话，先亮点后问题，前端原样展示、不加工
   请你回：确认？谁负责保证不泄露对方私有底牌？

【条款与协议】

6. status 全集
   我的默认：只有 pending / decided 两态
   请你回：还有 locked / waived 之类吗？枚举值给我
   不定的后果：漏判导致未决条款被签署（这是 UI 验收硬约束第 9 条）

7. 未决条款的"原因"
   我的默认：每个 pending 条款带一个 reason 字符串，前端在禁用的接受按钮上方
             逐条列出条款编号 + 原因
   请你回：有没有？字段名叫什么？
   不定的后果：只能我编原因，属于编造信息，不能进交付

8. 审计结果的数据形状
   我的默认：每条条款一个审计结论 + 一个整体结论
   现状：第一天原型抽屉里根本没有这个字段位
   请你回：形状、字段名、放在提交响应里还是单独接口？
   不定的后果：第 8 天做审计与评价联动时，抽屉没位置放

【态势与终局判定】

9. BATNA
   我的默认：我方真值由你给；对方恒显示"未知"；退出时"与 BATNA 比较"的
             结论由你算，前端只展示
   请你回：字段名？比较结论给什么形态（文本 or 数值差）？
   不定的后果：前端算比较 = 二次计算，违反数字同源

10. 随机议题检查 pass/conflict/idle
    我的默认：pass=可执行；conflict=参数冲突但保留原场景不覆盖进度；
              idle=未跑检查。三种都不阻塞报价
    请你回：含义对不对？conflict 到底阻不阻塞主流程？
    不定的后果：若 conflict 其实该阻塞，M2 固定场景闭环可能走不到终局

11. INVALID_ACTION 的定位粒度
    我的默认：detail 里指明哪一条款非法及原因，前端做行内红条定位到那一行
    请你回：能定位到条款吗？还是只有整单级文案？
    不定的后果：只能弹全局 toast，用户不知道改哪一条，来回试错

────────────────────────────────
定不了的回「待定 + 最晚哪天」，不要空着。
```

## 评审通过的判定标准

三条全满足才算 M1 冻结完成，可以进 T2：

| # | 条件 | 怎么验 |
| --- | --- | --- |
| 1 | 契约里每个字段都有**唯一 owner**，并标了「前端可写／只读」，没有任何「待定」字样残留在字段表里 | 全文搜 `待定`，应为 0 处（允许出现在"已知边界"一节） |
| 2 | 有一轮提交的**完整请求示例 + 成功响应示例 + 6 个错误码响应示例**，A 和 C 都说过「这就是我的实现口径」 | 聊天记录可截图，作为过程证据 |
| 3 | 上面 21 条全部有明确答复，包括「后端第 X 天才能定」这种带日期的结论 | 逐条打勾清单 |

**没通过怎么办**：手册 M1 的处置是「当晚完成跨模块评审，不能带着含糊字段进入开发」。
如果今晚确实定不完，优先钉死这 6 条（其余可以第 3 天边做边补）：

1. A-8 对方响应是同步还是异步 ← 决定你第 5～6 天工作量
2. A-2 version 谁递增 ← 决定 M2 闭环能不能验
3. A-1 幂等键承载方式 ← 决定提交层写法
4. C-6 条款 status 全集 + C-7 reason ← 决定接受按钮禁用逻辑
5. C-3 加权在哪边算 ← 决定复盘页有没有二次计算
6. A-7 请求体形状 ← 决定第 3 天报价板提交能不能落地
