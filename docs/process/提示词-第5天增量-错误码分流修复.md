# 背景（已核实的事实，不要怀疑）

A 的错误码清单 `API错误码清单.md`（仓库根）已给出真实错误码全集：
引擎 17 码（SCHEMA_VIOLATION / UNKNOWN_ACTION_TYPE / PATCH_NOT_ALLOWED / PHASE_CLOSED /
DUPLICATE_ACTION / VERSION_CONFLICT / AGREEMENT_HAS_OPEN_ISSUES / NO_COUNTERPART_OFFER /
ACTION_POINTS_INSUFFICIENT / UNKNOWN_CLAUSE / UNKNOWN_OPTION / TERM_LOCKED /
VALUE_OUT_OF_RANGE / REDLINE_VIOLATION / FINAL_OFFER_ALREADY_DECLARED / FINAL_OFFER_LOCKED /
FINAL_OFFER_EMPTY）+ API 层码（SESSION_BUSY=HTTP 409，MODEL_UNAVAILABLE=HTTP 503，
另有 400/404/405/422/500）。错误响应统一 {error, detail}。
VERSION_CONFLICT 的 409 响应额外携带 current_state（全量状态投影，含 my_offer /
opponent_offer / open_issues）。ROUND_LOCKED / TIMEOUT / INVALID_ACTION 后端不下发：
TIMEOUT 前端计时产生，INVALID_ACTION 是本地空草稿拦截（P6），ROUND_LOCKED 仅保留码位。

# 要修的 bug（根因相同：前端用 HTTP status 分流，但 status 与 error 是一对多）

## B1 · submit() 把 409 一律当版本冲突
现状（约 L147）：`if (r.status === 409)` → 无条件构造 `patch.serverVersion =
newestVersion(r.body, state.version + 1)`。
但清单写明 SESSION_BUSY 也是 409。服务忙时会塞入一个假的 serverVersion，污染合并逻辑。
要求：**以 body.error 为唯一分流依据**。只有 `error === "VERSION_CONFLICT"` 才走冲突分支、
才允许写 serverVersion；`error === "SESSION_BUSY"`（不管 status 是 409 还是别的）走排队重试分支，
**不得触碰 serverVersion / conflict**。

## B2 · 自动重试按 503 触发，但 503 是 MODEL_UNAVAILABLE
现状（约 L154）：`retryAfter: r.status === 503 ? 700 : 0`。
后果错位：模型挂了（503，该降级不该重试）反而获得自动重试；会话忙（409 SESSION_BUSY，
该自动重试 1 次）反而没有。
要求：重试策略只看 error 码——
- SESSION_BUSY：同幂等键自动重试 1 次、间隔 700ms，再失败转手动 toast，文案不变；
- MODEL_UNAVAILABLE：不重试，走左栏/情报降级空态，报价板照常（硬约束原样）；
- TIMEOUT：前端 150s 计时产生，同键可重试（原样）；
- 其余：不自动重试。

# 要补的 6 条专属路由（未知码兜底保持 K2：行内红条 + detail 原文，禁止静默——这条不变）

现在 mapError 把 SIX 之外的码全映射成 INVALID_ACTION"该行动不满足当前条款约束"。
不改映射总原则，但以下码加**专属 UI 路由**（store/组件层按 error 码分流，不再落通用红条）：

| 错误码 | 专属行为 |
| --- | --- |
| PHASE_CLOSED | 顶栏与手牌进入终局只读态（复用现有 ended 渲染），不是"行动不合法" |
| ACTION_POINTS_INSUFFICIENT | 拉取最新 ap 刷新手牌计数、手牌整条禁用——即原 ROUND_LOCKED 的行为，ROUND_LOCKED 保留码位兼容 |
| TERM_LOCKED / FINAL_OFFER_LOCKED / FINAL_OFFER_ALREADY_DECLARED | 行内红条定位到对应条款并显示锁定态；条款下拉禁用 |
| DUPLICATE_ACTION | toast 文案固定为「这笔行动已入账，未重复记账」（幂等拦截的服务端等价物，是 Demo 镜头 06 的证据文案，不得显示"不满足条款约束"） |
| AGREEMENT_HAS_OPEN_ISSUES / NO_COUNTERPART_OFFER | 在协议抽屉内、接受按钮上方逐条解释（复用未决条款 pending 解释的同一 UI），不是全局红条 |
| VALUE_OUT_OF_RANGE / UNKNOWN_OPTION / UNKNOWN_CLAUSE / SCHEMA_VIOLATION / UNKNOWN_ACTION_TYPE / PATCH_NOT_ALLOWED / REDLINE_VIOLATION / FINAL_OFFER_EMPTY | 维持 K2 通用行内红条 + detail 原文 |

# 要利用的新信息：409 携带 current_state

现状 merge() 用 `GET /session/state` 拿最新基线。清单确认 VERSION_CONFLICT 的 409 响应
已带全量投影（my_offer / opponent_offer / open_issues）。
要求：VERSION_CONFLICT 分支**优先直接消费 current_state** 更新基线版本、对方报价与 open_issues
（草稿保留、selectedCard 保留，硬约束不变）；仅当响应缺 current_state 时回落现有
`GET /session/state`。消费 open_issues 时注意条款匹配用 id（若 current_state 给的是 name 键，
按现有 G4 宽容解析，匹配不上标 unknown 不静默变 decided）。
