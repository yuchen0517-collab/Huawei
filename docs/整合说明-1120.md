## 5. 整合时发现并修掉的真实问题

1. **`clause_roles` 的 id/name 口径不一致（会导致卡牌全被拒）。**
   B 的契约用 `issue_id` 声明（`{"condition": "I3", ...}`），而引擎的 `offer_patch` 以**条款名**为键，
   `negotiation_rules.check_card_action` 与前端 `target_clause` 也都按条款名比对。直接收编后
   `role_clause` 会返回 `"I3"`，任何报价都会被判 `CARD_PAYLOAD_INVALID`。
   修复：`adapter/scenario_adapter.py` 新增 `_adapt_clause_roles()`，在 B→C 转换时把 `issue_id`
   映射成条款名；`scenario_overrides.apply_overrides` 只做存在性校验，兜底表同步改为新条款名。

2. **B 删掉数值议题 I2 后，a 分支的测试夹具全部指向已不存在的条款。**
   7 个测试文件的 `NUMERIC_PATCH` / `EXPECTED_ROLES` / 卡牌 `target_clause` 断言仍写「许可审批时限」，
   收编瞬间 50 条用例失败。按新场景（I1 数值 + I3/I4/I5 枚举）统一改写，并补一条「场景自带
   `clause_roles` 也要校验」的用例。

3. **`.gitignore` 被 C 分支简化后失去安全条目**（见 §4），改为在 a 分支版本上做加法。

### 8.2 已解决：评分口径统一（BACKLOG #9）

B 的 `zopa.py` 与引擎 `engine/indices.py` 原本是两套打分，同一份方案会得出相反结论：

| 场景 | 引擎（App 口径） | zopa（B 测试/QA 口径） | BATNA | 原状 |
|---|---|---|---|---|
| main | 82.55 / 66.29 | 67.86 / 48.21 | 40 / 35 | 结论一致、数值不同 |
| no_zopa | 93.16 / 53.37 | 35.89 / 28.57 | 40 / 35 | **结论相反** |
| backup | 77.50 / 41.67 | 66.25 / 41.67 | 38 / 35 | 结论一致、数值不同 |

四处根因（都在统一过程中才暴露）：

1. **numeric 用整段物理区间算 closeness**，踩红线（800/1500）仍有 0.857 分，导致「碰红线的协议净赚」。
   改为**红线锚定**：红线 0、目标 1、超过目标封顶（`engine/indices.py::score`）。
2. **enumerated 用 order 反推 P2**（隐含「双方偏好完全相反」），而实际 P1 目标 O2、P2 目标 O3。
   改为**逐方按 target 位次衰减**（`zopa.py` 与适配层 `_ranked_scores` 同一公式）。
3. **部分协议把未谈成的议题按现状值计入效用**，等于把没签下的条款算成收益。
   新增 `terminal.package_utility`，协议评价与 BATNA 比较只计协议包内条款（与手册 5.2「其余议题被搁置」一致）；
   过程指数 `interest` 仍按现状延续，两者用途分开。
4. **适配层从红线方向推断偏好方向**，遇到「越高越好 + 上限红线」会判反
   （backup 的追溯适用期：引擎 1.0、zopa 0.0）。改为透传 `goals[].direction`，引擎优先采用。

同时修了 `suggest_deal` 的结构性偏袒：原实现取每个议题 order 最小的选项（order=1 恒为 P1 最优），
backup 因此给出 63.75 / 28.33（P2 低于 BATNA）；改为可行域 max-min 均衡点后为 52.5 / 46.67。

统一后两边逐项相等：

| 场景 | 参考方案 | 双方效用 vs BATNA |
|---|---|---|
| main | I1=1150, I3=O2, I4=O2, I5=O2 | 65.0 > 40 ✅ / 55.83 > 35 ✅ |
| backup | I1=3, I2=O2, I3=0, I4=O3 | 52.5 > 38 ✅ / 46.67 > 35 ✅ |
| no_zopa | I1=1150, I3=O2, I5=O2 | 35.0 < 40 ❌ / 31.67 < 35 ❌（理性退出成立） |

防回归：`check_score_alignment.py` 重写为 zopa↔引擎逐项比对（值差 < 0.05、BATNA 结论必须一致），
并由 `test_score_parity.py` 固化为测试。

### 8.5 第三轮：场景化 Prompt 与逐方评分（BACKLOG #3、#4 收口）

1. **对手 System Prompt 改为按运行时场景生成（`prompt_context.py`）。**
   原先 `api.py` 直接用 `SYSTEM_PROMPTS[agent]`，而那份 prompt 的占位符全部来自
   `agents.json` 的《全球AI治理框架公约》题材；加载芯片/DST 场景时，对手会用 AI 治理
   代表的口吻发言。现在自定义场景的 prompt 由场景派生：主题、会议场合、议题、
   本方公开立场、按权重排序的目标、红线（数值红线 + 枚举禁用项）、BATNA、
   隐藏任务卡，外加场景自带的事实卡与教学假设。默认 `ai_governance` 仍用手写文案，
   不动已打磨的演示话术。

2. **初始三项指数改为取场景 `index_rules`。**
   原先固定读 `agents.json` 的 50/70/65；芯片场景实际声明的是 us 55/40（image/trust）
   与 interest 31。现在非默认场景用 `engine.indices.initial_indices(scenario)`。

3. **三份 B 场景补齐 `options[].score_by_party`。**
   取值等于当前推导值（各自 target 为 1.0、按 order 位次衰减），所以引擎与 zopa 的
   数值一分不差；作用是把「隐式推导」变成「显式数据」，B 想微调偏好时直接改场景，
   不用改代码。三份场景 `validate_scenario` 均 0 问题（R16 要求同方同议题给全，已满足）。

回归：`test_scenario_prompt.py` 4 条——prompt 不再含 AI 治理题材、含场景 BATNA 与隐藏任务、
不泄露对方私牌、API 建会话的初始指数等于场景声明、默认场景不被改动。
`check_score_alignment.py` 仍 6/6 一致。
