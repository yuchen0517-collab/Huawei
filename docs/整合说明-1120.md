## 5. 整合时发现并修掉的真实问题

1. **`clause_roles` 的 id/name 口径不一致（会导致卡牌全被拒）。**
   B 的契约用 `issue_id` 声明（`{"condition": "I3", ...}`），而引擎的 `offer_patch` 以**条款名**为键，
   `negotiation_rules.check_card_action` 与前端 `target_clause` 也都按条款名比对。直接收编后
   `role_clause` 会返回 `"I3"`，任何报价都会被判 `CARD_PAYLOAD_INVALID`。
   修复：`adapter/scenario_adapter.py` 新增 `_adapt_clause_roles()`，在 B→C 转换时把 `issue_id`
   映射成条款名；`scenario_overrides.apply_overrides` 只做存在性校验，兜底表同步改为新条款名。

2. **B 删掉数值议题 I2 后，a 分支的测试夹具全部指向已不存在的条款。**
   7 个测试文件的 `NUMERIC_PATCH` / `EXPECTED_ROLES` / 卡牌 `target_clause` 断言仍写「许可审批时限」，
   收编瞬间 50 条用例失败。按新场景（I1 数值 + I3/I4/I5 枚举）统一改写，并补一条「场景自带
   `clause_roles` 也要校验」的用例。

3. **`.gitignore` 被 C 分支简化后失去安全条目**（见 §4），改为在 a 分支版本上做加法。

## 7. 已知未解项（不在本次收编范围）

1. **B 侧 `test_no_zopa_variant_leads_to_rational_exit` 失败。**
   已在 `origin/feat/scenario-b`（`7b97993`）上单跑复现，属于 B 交付自带问题：
   `no_zopa_variant.json` 被改版后，`suggest_deal` 给出的方案对双方都高于 BATNA，
   与「无合作区间、理性退出」的设计意图相反。这是 B 的场景数据问题，不擅自改 B 的数据，需 B 复核权重/红线。
2. **`check_score_alignment.py` 仍报 6 处排名不一致、16 处分数不一致。**
   在收编前的 a 分支上即为 6 / 12，属既有诊断项（B 场景缺显式逐方选项分，回落 order 推导），非本次回归。
3. **编排层尚未接进 `api.py`。** `orchestrator.py` 目前只由 `run_workflow.py` 与测试驱动；
   `SCHEDULER_HANDOFF.md` 给的是接入方式，是否把 HTTP 会话主链路切到编排状态机，需要 A 决策后再动。
4. **`est_confidence` 仍为 `null`。** 引擎只预留字段，定性分级由 UI 侧推导。
5. **D 的 UI 与 coach 前端未收编。** 待 `feat/ui-coach-d` 定稿后单独合入，届时需复核 `openapi.json`（D 分支上的
   版本是 4 KB 的旧桩，a 分支为 39 KB 的完整契约，不可覆盖）。
6. **合入 D 的教练面板前必须先对齐 `kind` 枚举（阻塞项）。**
   a 分支服务端已按 11-17 回签值返回 `kind ∈ {risk, opportunity, next_move}`（见 `api.py::build_coach_advice`），
   而 D 分支的前端仍是旧口径 `stage / alternative`：
   - `教练Agent/src/components/coach.js`：`KIND_LABEL = { stage: "阶段建议", alternative: "替代行动" }`
   - `P0五项/src/components/CoachPanel.js`、`P0五项/src/services/coach.js` 同样按旧值分支

   直接接 a 的接口，所有条目都会被渲染成「阶段建议」，`risk` 与 `next_move` 的样式与文案全部走错分支。
   两条路：D 侧改成三值（契约文档 §1.2 已自行标注「待重构」），或合入时在前端加一层兼容映射。
   另外 `ap_cost` 在服务端目前恒为 `1`（`next_move`）或 `null`，与契约要求一致，但 `apply_hint` 恒为 `null`，
   属于契约预留未启用，不是缺陷。
