# 谈判页差距对比：纪要 v2 决议 vs 现有新 UI

> 对照对象：`外交谈判智能体升级改造头脑风暴纪要.docx`（11-10 讨论 + 11-16「决议与契约 v2」追加章）
> 现状基准：`Diplomat-components(1)` 路径 B 已验收版本（`Diplomat-单文件版.html`）
> 口径：**§12 标「已定」的按硬需求对待**；§1–§11 属头脑风暴建议，标注为「待团队确认」，不直接当需求做。

---

## 一、结论先说

1. **卡牌层已经有了，但只做了「策略卡」一层**。纪要的核心交互是三层——策略卡 / 议题报价板 / 协议签署板，现在第二层被塞进了「战报」弹窗（只读、下拉框不写状态），第三层完全不存在。
2. **最重要的缺口不是视觉，是「谈判没有可判定的终点」**。现在终局=轮次耗尽弹窗；纪要 §3.2 要求五种终局（完整协议/部分协议/主动退出/僵局终止/回合耗尽），§3.3 还要求把「谈判结果 / 协议质量 / 学习表现」三个维度分开评。这一条直接决定 Demo 能不能讲「系统凭什么判定这一局结束」。
3. **规则层缺三个可见的状态机**：§12.4 响应闭包（待表态窗口 + 1 次过渡额度）、§12.5 冷却、§12.1 僵局阈值（连续 3 轮无新版本）。这三样现在界面上一个都看不到，评审问「你怎么防止无限拖延」时没有画面可指。

## 二、逐项对照（按谈判页可见性排序）

### A. 三层交互

| 项 | 纪要要求 | 现状 | 差距 |
|---|---|---|---|
| 策略卡层 | §5.2/§5.3：卡牌决定「用什么策略」，按卡牌要求指定议题、条件、目标 | 左栏 5 张卡（1/1/2/1/2 AP），只有名称/描述/效果，**没有族标签、没有冷却、没有「是否需要提交条款」提示** | ⚠️ 部分：只有壳 |
| 议题报价板 | §5.2：显示我方上一版 / 对方最新版 / 当前分歧 / 条款差异，用户改选项、设让步对价、提交反报价 | 条款表在**战报弹窗**里：5 条固定条款 + 我方下拉 + 对方估计 + 状态；下拉不写状态、不产生版本、不进主流程 | ❌ 实质缺失：位置错、不写版本 |
| 协议签署板 | §5.2：已一致条款 / 待确认条款 / 协议版本 / 履约风险；签署、继续还价、最后报价、部分签署、退出 | 完全没有 | ❌ 缺失 |
| 报价板法则 | §12.2：产出要写进协议对象的牌才走报价板，其余打完即结束回合 | 现在所有卡点「结束本轮」都走同一条提交链路，不区分是否产生版本 | ❌ 缺失（含 UI 与提交链路） |
| 条款变化摘要 | §5.5：对方回应后先高亮「接受了哪条、修改了哪条、还剩几项分歧」 | 回应只有一段话 + 一个「顾问研判」灰条 | ❌ 缺失 |

### B. 行动与规则

| 项 | 纪要要求 | 现状 | 差距 |
|---|---|---|---|

| 过渡额度 | §12.1：每个版本 1 次 | 无 | ❌ 缺失 |
| 卡牌冷却 | §12.5：报价塑造/条款控制/立场表态冷却 1 回合；信息试探 2；核查履约 3；程序类与最后报价每局 1 次 | 无冷却，同一张卡可连续点 | ❌ 缺失 |

| 僵局计时 | §12.1/§12.5：连续 3 轮无新版本判僵局（双方该轮均无新版本） | 只有 maxRounds=15 的回合上限，没有任何僵局提示 | ❌ 缺失 |
| 卡池规模 | §12.3：14 张牌 / 6 族 + 6 个基础行动；常驻持有、不抽牌、用后冷却 | 5 张卡，无族划分 | ⚠️ 内容与结构都要换（依赖 B 产出的 card_registry） |
| 承诺账本 | §12.3：公开承诺进入承诺账本；§12.7 尚未存储 | 无 | ❌ 缺失（后端先缺） |

### C. 终局与评价

| 项 | 纪要要求 | 现状 | 差距 |

## 三、建议优先添加（P0，能进 11-24 前 Demo）

### P0-1 基础行动条（§5.4）
- 位置：中栏「公开会场」输入区下方（现在只有发言流，底部空着），或左栏手牌区与「结束本轮」并排的一行 secondary 按钮。
- 内容：`接受当前协议` / `拒绝` / `维持原报价` / `最后报价` / `宣布退出` 五个按钮，始终可点（除已终局/轮次锁定）。
- 口径：每个按钮=一次行动，走与策略卡相同的 `submitAction`（复用幂等 `action_id`、六错误码、草稿保留）；`接受/退出` 需要二次确认（不可撤销）。
- 工作量：小（1 天）。不依赖 A/B。

### P0-2 协议签署板（§5.2 第三层）
- 位置：中栏右侧滑出抽屉（与谈判树同款），或右栏「态势」下方折叠区。
- 内容：三条分区——`已一致` / `待确认（几项）` / `履约风险提示`，顶部显示 `协议版本 vX`；底部四个动作：`签署完整协议` / `部分签署` / `继续还价` / `退出`。
- 数据：把战报里的 5 条条款表搬进主流程并接状态（`clauses[]` 由 store 持有），战报改为只读快照。
- 工作量：中（1.5～2 天）。新增 `clauses` 到 store（已规划但未落），不依赖 A。

### P0-3 待表态窗口 + 过渡额度（§12.4）
- 位置：中栏顶部一条状态带（消息流上方），显示「对方待表态 · 过渡额度 1/1」；额度用完时提示「本轮必须接受 / 拒绝 / 反报价 / 最后报价」。
- 行为：窗口关闭前，`提交新版本` 按钮置灰并解释原因（引用 §12.4，不改文案风格）。
- 工作量：小～中（1 天），纯前端状态机，可在 mock 下完整演示。

### P0-4 条款变化摘要（§5.5）
- 位置：对方每轮回应气泡顶部一行 chip：`接受 2 条 · 修改 1 条 · 剩余 3 项分歧`，点击展开条款 diff。
- 工作量：小（0.5 天）。数据来自 `applyTurn` 的返回 patch。

### P0-5 僵局与终局五态（§3.2 / §12.1）
- 位置：顶栏 ROUND 旁加「僵局计时 0/3」；终局弹窗按五态给不同标题与结论句，并区分「协议质量」与「学习表现」两块。
- 工作量：中（1～1.5 天）。前端可先按规则算，等 A 的终局端点接管判定。

**合计约 5～6 天**，其中 P0-1/3/4 不依赖任何人，可今天开工；P0-2 需要先把 `clauses` 加进 store；P0-5 的判定权最终归 A。

## 五、先不做 / 要团队拍板

- **多方扩容**（§8.2 建议退出主线）、复杂暗线、更多表现层效果（§9.1 列 P2）——不做。
- **分支推演 / 暂停接管 / 同局重跑**（§6.1）：演示故事线第 4～5 步要用，但需要状态快照与回放，属 P1，建议 11-20 后再评估。
- **可谈判性检查 + 场景确认页**（§7.2/§7.4）：属「输入议题」入口，和当前写死议题的实现冲突，需队长先定 Demo 是否现场输入议题。
- **承诺账本 / 信息集**（§12.7 明确未尽）：后端未存储，前端只能占位，等 A/B。
- **行动点 4/5、14 张卡**：与现有 5 张卡验收结果冲突，改口径前先跟 A/B 对齐，别前端单方面改。

---

## 六、一句话给团队

谈判页现在「能演」，但还不能「被判」。补上 **基础行动条 + 协议签署板 + 待表态窗口** 这三样，页面上才第一次出现「这一局凭什么结束」的答案；其余（终局五态、僵局计时、条款摘要）是把这个答案讲清楚。
